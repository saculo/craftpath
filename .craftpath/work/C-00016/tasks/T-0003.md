# T-0003 — Fix only the fix points

- **Work:** C-00016
- **Type:** feat
- **Wave:** 3
- **Depends on:** T-0002
- **Touches:** assets/scripts/guards/verify-fix.py, assets/scripts/verify-fix.py, assets/scripts/checks.py (check_verify_fix), assets/steps/verify-fix.md
- **Scenarios:** S3, S4, S8, S9

## Acceptance criteria

- **A1** Given `VERIFY.md` with open `[you]` F2 and `[noted]` F3 and no open `[fix]`, when verify-fix runs, then it is refused with "Nothing to fix: no `[fix]` point is open", and `PLAN.md` and the tasks directory are unchanged — proven by integration test `verify-fix is refused with only you and noted points open`
- **A2** Given open `[fix]` F1, `[you]` F2 and `[noted]` F3, when verify-fix.py runs, then it lists F1 under Open points and does not list F2 or F3 — proven by integration test `verify-fix.py lists only the open fix points`
- **A3** Given those same points and one new fix task whose Fixes is `F1`, when `check.py verify-fix` runs, then it passes; and given a second new task whose Fixes is `F2` (or `F3`), it fails saying F2 is not an open fix point — proven by integration test `the verify-fix check names only fix points`
- **A4** Given a `[you]` point F2 the user retagged to `[fix]`, when verify-fix runs, then it lists F2 and the check requires a task for it — proven by integration test `a retagged you point is fixed like any fix point`
- **A5** Given a `[you]` point F2 marked `- [-] F2 [you] ... (won't fix: not wanted)`, when verify-fix runs with no open `[fix]`, then it is refused as in A1, naming no F2 task — proven by integration test `a declined you point asks for no task`
- **A6** Given the step installed for Claude Code and for pi, when its text is read, then both say verify-fix handles `[fix]` points only and runs the same script — proven by integration test `verify-fix is installed on both harnesses for fix points only`

## Notes

A refusal, not an exit 0, for "nothing to fix": it is the mechanism the guard
already uses for "no point is open" (decided; the loop in T-0006 checks for an
open `[fix]` before it calls verify-fix, so the refusal is never hit in a
normal run). The existing message in the guard and its test change from "no
verify point is open" to name `[fix]`.
