# T-0005 — Refuse a third verify round

- **Work:** C-00016
- **Type:** feat
- **Wave:** 5
- **Depends on:** T-0004
- **Touches:** assets/scripts/verify.py, assets/scripts/guards/verify.py
- **Scenarios:** S6, S7

## Acceptance criteria

- **A1** Given a work item with an open `[fix]` point, when `verify.py <work id> --round 3` runs, then it is refused, the refusal names each open `[fix]` point by id, and VERIFY.md is unchanged and no test run starts — proven by integration test `verify refuses round 3 and names the open fix points`
- **A2** Given the same work item, when `verify.py <work id> --round 2` runs, then it runs as for round 1 (tests, then VERIFY.md) — proven by integration test `verify runs in round 2`
- **A3** Given `verify.py <work id>` with no `--round`, when it runs, then it behaves as round 1 — proven by integration test `verify without a round is round 1`
- **A4** Given round 3 and no open `[fix]` point, when `verify.py --round 3` runs, then it is refused all the same, naming no point — proven by integration test `round 3 is refused even with nothing open`

## Notes

The cap is enforced by a mechanism, not only by the step's prose: the loop in
T-0006 passes `--round <n>`, and the script is the one place that says no
(decided: a model counting rounds in its own head is the failure the cap
exists to stop). The user's own `verify <id>` has no `--round`, so it is
round 1: a fresh invocation, with its own two rounds (SPEC assumption).
`work_item` parses the argument string; `--round` is stripped before the work id
is read. Keep the option out of the user-facing argument hint.

- `--round` is parsed and the cap enforced in `verify.py` (`split_round`, after `work_item`, before `run_tests`). `guards/verify.py` is unchanged: it reads the work id first, so `<id> --round n` already passes through it.
- `.craftpath/manifest.json` changed because `init` was re-run; the installed `.craftpath/scripts/verify.py` is the regenerated copy.
