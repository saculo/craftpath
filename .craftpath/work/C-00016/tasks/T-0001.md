# T-0001 — Tag verify points fix, you or noted

- **Work:** C-00016
- **Type:** feat
- **Wave:** 1
- **Depends on:** none
- **Touches:** assets/scripts/checks.py, assets/templates/VERIFY.md, the verify check's existing test fixtures
- **Scenarios:** S1

## Acceptance criteria

- **A1** Given a `VERIFY.md` whose points are tagged `[fix]`, `[you]` and `[noted]`, each with `file:line` and a failure scenario, when `check.py verify` runs, then it reports no problem — proven by integration test `check verify accepts the fix, you and noted categories`
- **A2** Given a `VERIFY.md` with `- [ ] F1 [major] src/a.ts:3 -- given x, y` (and again with `[minor]`), when `check.py verify` runs, then it fails naming F1 and listing `fix`, `you` and `noted` as the tags to use, and `verify_points` returns no point for the line — proven by integration test `check verify rejects the major and minor tags`
- **A3** Given a point with no tag or an unknown tag (`[later]`), when `check.py verify` runs, then it fails naming the point and writes nothing — proven by integration test `check verify rejects a point without a category`
- **A4** Given a freshly created `VERIFY.md`, when its template is read, then the guidance and the example line name `[fix|you|noted]` and not `[major|minor]` — proven by integration test `the verify template names the three categories`

## Notes

Data shape first, because every later task reads it: a point is
`- [ ] F<n> [fix|you|noted] <file:line> -- given <input or state>, <what goes wrong>`.
The id stays `F<n>` as C-00015 built it, not the `V<n>` the spec's S9 writes
(decided: renaming would break `Fixes: F<n>`, the verify-fix check and C-00015's
fixtures for no behaviour). The tag set lives in one place, `FINDING` in
`checks.py`, and `verify_points` keeps returning `(state, id, line)`; the
category is read from the line by a small helper the next tasks use, so no
caller's tuple shape changes.

Existing tests and fixtures in `test/steps/` that write `[major]` or `[minor]`
change to a category in this task (they would fail otherwise); that is
fixture upkeep, not new behaviour. Use `[fix]` for them, which keeps their
meaning (open and fixable) until T-0002 and T-0003 give categories their own
behaviour.
