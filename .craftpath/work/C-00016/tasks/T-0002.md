# T-0002 — Block the pull request on fix and you points only

- **Work:** C-00016
- **Type:** feat
- **Wave:** 2
- **Depends on:** T-0001
- **Touches:** assets/scripts/checks.py (verify_closed), assets/scripts/pr.py
- **Scenarios:** S9, S10

## Acceptance criteria

- **A1** Given `VERIFY.md` with an open `[fix]` point F1 and a closed one, when pr runs, then it is refused naming F1 and pushes nothing — proven by integration test `pr is refused while a fix point is open`
- **A2** Given `VERIFY.md` with an open `[you]` point F2, when pr runs, then it is refused naming F2 and pushes nothing — proven by integration test `pr is refused while a you point is open`
- **A3** Given `VERIFY.md` whose only open point is `[noted]` F3, when pr runs, then it pushes, opens the pull request, and the body's Verify section contains the F3 line verbatim — proven by integration test `pr proceeds with a noted point open and lists it`
- **A4** Given an open `[you]` point F2 that the user marked `- [-] F2 [you] ... (won't fix: out of scope)`, when pr runs, then it proceeds and the body lists F2 as the user wrote it — proven by integration test `pr proceeds once a you point is declined`
- **A5** Given an open `[noted]` point, when learn runs, then it is not refused for that point (learn uses the same gate) — proven by integration test `learn proceeds with a noted point open`

## Notes

`verify_closed` is the single gate pr, learn and verify.py share, so the change
is one predicate: a point blocks when it is open and its category is `fix` or
`you`. Its refusal text names both. Retagging a `[you]` point to `[fix]` is
just an edit to the line; no code beyond the category read handles it (it is
proven in T-0003 where the loop reads it).
