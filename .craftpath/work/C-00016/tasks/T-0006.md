## Acceptance criteria

- **A1** Given the verify step installed for Claude Code and for pi, when its text is read, then after writing `VERIFY.md` it says: if an open `[fix]` point exists, run `verify-fix`, then `work <id> all`, then `verify <id> --round 2`, and make exactly one task per open `[fix]` point and none for `[you]` or `[noted]` — proven by integration test `verify loops fix then work then verify on both harnesses`
- **A2** Given the installed step, when its text is read, then it says to stop without a further round when no `[fix]` point is open after a round, and to report the open `[you]` points and the `[noted]` ones — proven by integration test `verify stops when no fix point is open`
- **A3** Given the installed step, when its text is read, then it says to stop after round 2 even with a `[fix]` point open, to report those points by id, and to start no further fix round — proven by integration test `verify stops after two rounds and reports the open fix points`
- **A4** Given the installed step, when its text is read, then it tells the user to answer a `[you]` point by retagging it `[fix]` or marking it `[-]` with `(won't fix: <reason>)` and running verify again, and mentions no new command — proven by integration test `verify tells the user how to answer a you point`
- **A5** Given the Claude Code and pi installs, when the verify step is compared with placeholders resolved, then the loop, the 2-round cap and the categories are the same text on both — proven by integration test `both harnesses carry the same verify loop`
- **A6** Given the installed verify step, when its text is read, then it never tells the agent to ask the user before fixing a `[fix]` point — proven by integration test `verify does not ask before fixing a fix point`

## Notes

The loop is the verify step's own instructions, run in the user's session (verify
already is one; verify-fix is delegated and work is run from it). Rounds are
counted by passing `--round` (T-0005) so the cap is not left to the model.
Fix tasks are added to the finished plan by verify-fix (C-00015) and run with
`work <id> all`, which runs only the unticked ones.

Out of this task, by the spec: more than 2 rounds, a configurable cap.

- The loop is step 6 of `assets/steps/verify.md`, same text on both harnesses (only command placeholders differ). Round 2 is detected by `--round 2` in the arguments (T-0005 refuses round 3).
