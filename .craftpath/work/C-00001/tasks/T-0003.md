# T-0003 — Show the step settings commented out in a fresh config.toml

- **Work:** C-00001
- **Type:** feat
- **Wave:** 3
- **Depends on:** T-0001
- **Touches:** src/init.ts, README.md, test/init/init.test.ts
- **Scenarios:** S6

## Acceptance criteria

- **A1** Given a project with no `.craftpath/config.toml`, when `init --harness claude-code` runs, then the config.toml it writes contains the commented-out lines `# [steps.work.claude-code]`, `# model = "sonnet"`, `# [steps.review.claude-code]` and `# model = "opus"`, in that order, and `Bun.TOML.parse` of it has no `steps` key — proven by integration test `a fresh config shows the step settings commented out`
- **A2** Given a project with no `.craftpath/config.toml`, when `init --harness claude-code` runs, then every `.claude/skills/craftpath-<step>/SKILL.md` it installs is byte-for-byte the file installed in a project whose existing config.toml has no `[steps]` table — proven by integration test `the commented example applies nothing`
- **A3** Given a project whose `.craftpath/config.toml` already exists without the example, when `init --harness claude-code` runs, then config.toml is byte-for-byte unchanged and contains no `steps.` text — proven by integration test `an existing config is not given the example`

## Notes

- Skills: `backend`.
- Wave 3 only because every task here is in module `app`; it needs nothing from
  T-0002. It depends on T-0001 for the config shape the example must match: once
  uncommented, the example has to be exactly what T-0001 reads.
- Suggested block, appended to the fresh config after `[modules.app]`:
  ```toml
  # Model and effort per step, on Claude Code. Re-run `craftpath init` after
  # changing them. work's setting applies to the subagent it starts per task.
  # [steps.work.claude-code]
  # model = "sonnet"
  # effort = "medium"
  #
  # [steps.review.claude-code]
  # model = "opus"
  # effort = "high"
  ```
  The effort lines are optional; A1 does not require them.
- README: add a short paragraph next to the existing config.toml description
  (around "`.craftpath/config.toml` lists the project's modules") naming the
  `[steps.<step>.claude-code]` table, that work's setting goes to its task
  subagents, that pi ignores it, and that it takes effect on the next
  `craftpath init`. `test/readme.test.ts` must stay green: write the step as
  `/craftpath-work`, not a new spelling.
- **Implementation notes (T-0003):**
  - A1 failed first on the missing commented lines. A2 and A3 passed on their
    first run because they guard something that did not exist yet. Each was then
    made to fail by a temporary mutation of `writeConfig`: uncommenting the
    review example breaks A2, and appending to an existing config breaks A3.
    Both mutations were reverted.
  - **Deviation from the suggested block:** the separator between the two
    commented tables is a blank line, not a bare `#`. Bun 1.3.10's
    `Bun.TOML.parse` drops a table header that directly follows a bare `#`
    line: `"[a]\nx = 1\n#\n[b.c]\ny = 2\n"` parses as `{a:{x:1,y:2}}`. With
    the suggested block, a user who uncommented only the review lines would
    have had `model = "opus"` land silently in `[modules.app]`. The A2
    mutation exposed this, because it stayed green until the `#` was replaced.
    `# ` (with a trailing space) and a blank line both parse correctly. This
    trap exists for any user-written config.toml too, but guarding against it
    is outside this task.
  - README: the paragraph and example sit after the modules text in the
    "Modules" section; the step is written `/craftpath-work`.
