# T-0001 — Apply a step's configured settings to its Claude Code skill

- **Work:** C-00001
- **Type:** feat
- **Wave:** 1
- **Depends on:** none
- **Touches:** src/init.ts, src/harness.ts, test/init/init.test.ts
- **Scenarios:** S1, S3, S4, S5, S7

## Acceptance criteria

- **A1** Given a project whose `.craftpath/config.toml` has `[steps.review.claude-code]` with `model = "opus"` and `effort = "high"`, when `init --harness claude-code` runs, then `.claude/skills/craftpath-review/SKILL.md` has the front-matter lines `model: opus` and `effort: high`, and every other `.claude/skills/craftpath-<step>/SKILL.md` (work and brainstorm included) is byte-for-byte the file `init` installs in a project with no `[steps]` table — proven by integration test `a configured step runs with its model and effort`
- **A2** Given `[steps.review.claude-code]` with only `model = "opus"`, when `init --harness claude-code` runs, then `.claude/skills/craftpath-review/SKILL.md` has the front-matter line `model: opus` and no line starting `effort:` — proven by integration test `only the model is set when only the model is configured`
- **A3** Given a project installed by `init --harness claude-code` with a config.toml that has no `[steps]` table, when `init --harness claude-code` runs again, then its output names no `.claude/skills/craftpath-` file, and no installed step file has a front-matter line starting `model:` or `effort:` — proven by integration test `a config without step settings installs the steps as before`
- **A4** Given a project installed with no `[steps]` table, to whose config.toml the user then appends `[steps.review.claude-code]` with `model = "opus"`, when `init --harness claude-code` is re-run, then its output contains `updated   .claude/skills/craftpath-review/SKILL.md`, that file has `model: opus`, and `.craftpath/config.toml` is byte-for-byte what the user wrote (no line added, removed or reformatted) — proven by integration test `a setting added later takes effect on the next init and leaves config.toml alone`
- **A5** Given a project with `[steps.review.claude-code]` `model = "opus"`, when `init --harness claude-code,pi` runs, then `.claude/skills/craftpath-review/SKILL.md` has `model: opus`, and every `.pi/skills/craftpath-<step>/SKILL.md` is byte-for-byte the file `init --harness claude-code,pi` installs with no `[steps]` table — proven by integration test `a Claude Code step setting leaves every pi step untouched`

## Notes

- Skills: `backend` (a CLI's file-writing path; there is no server here).
- **Config shape (decided here, local to this work item):** one table per step
  and harness, keys optional:
  ```toml
  [steps.review.claude-code]
  model = "opus"     # passed through as written: an alias or a full model id
  effort = "high"
  ```
  T-0002 reads the same table for `work`, and T-0003 writes it, commented out,
  into a fresh config.toml -- keep the shape exactly this.
- `init` reads config.toml after `writeConfig` (so a freshly written one counts)
  with `Bun.TOML.parse`, and hands each step's `claude-code` settings to
  `CLAUDE_CODE.renderStep`. Only the keys that are set become front-matter lines
  (`model: <value>`, `effort: <value>`), appended after the existing ones. pi's
  `renderStep` ignores settings entirely.
- **work is excluded here:** a `[steps.work.claude-code]` setting must never
  become front matter on the work skill (S2: work itself runs on the session
  model). This task simply does not apply work's setting at all; T-0002 makes it
  reach work's subagents.
- Out of scope per SPEC, simplest behaviour chosen: an unknown step name or
  harness key is ignored; values are not validated; a config.toml that does not
  parse is treated as having no step settings (the Python scripts already refuse
  it with a clear message on the next step).
- Build A1/A5's "byte-for-byte" baselines by running `init` in a second scratch
  project with the same harnesses and no `[steps]` table, then comparing file
  text -- not by hard-coding expected content.
