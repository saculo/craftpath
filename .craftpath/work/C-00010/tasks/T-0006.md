# T-0006 — Retire the discipline skills

- **Work:** C-00010
- **Type:** feat
- **Wave:** 6

## Acceptance criteria

- **A1** Given a project with no craftpath, when `init(root, ["--harness", "claude-code,pi"])` runs, then none of `{.claude,.pi}/skills/{backend,frontend,infrastructure}` exists as a directory, and both `.claude/skills/ux/SKILL.md`, `.claude/skills/architecture/SKILL.md` and their `.pi` counterparts exist — proven by integration test `a fresh install ships no discipline skills but keeps ux and architecture`
- **A2** Given a project initialised on both harnesses from an earlier asset set that ships `skills/{backend,frontend,infrastructure}/SKILL.md`, none edited, when `init` runs again with the current assets, then all six installed `SKILL.md` files are gone, the output has the line `removed   <path>` for each of the six, and `.craftpath/manifest.json` lists none of them — proven by integration test `re-running init retires the unedited discipline skills`
- **A3** Given the same earlier project, when `init` runs again, then every other `{.claude,.pi}/skills/*/SKILL.md` that the current assets ship is still present and no output line `removed   ` names any path outside the six — proven by integration test `retiring the discipline skills removes nothing else`
- **A4** Given the same earlier project where `.claude/skills/backend/SKILL.md` was overwritten with `# my backend notes\n` after the first init, when `init` runs again, then that file still reads exactly `# my backend notes\n`, the output contains `kept      .claude/skills/backend/SKILL.md (edited)`, and the other five discipline `SKILL.md` files are removed — proven by integration test `re-running init keeps an edited discipline skill`

## Notes

- Build the "earlier asset set" as `reinitializing retires the managed testing
  skill` does: `cp` `ASSETS` to a scratch dir and write the three
  `skills/<name>/SKILL.md` into it, then `init(..., { assets: earlier })`
  followed by a plain `init`. Write these tests first: they fail while
  `assets/skills/backend` etc. still exist (nothing is retired), and the
  retirement code path is not reached for those names.
- Generalise `retireTestingSkill` in `src/init.ts` to a list of retired
  skills (`testing`, `backend`, `frontend`, `infrastructure`), each
  retired only when the asset set no longer ships it -- same rule as today: a
  hash matching the manifest is removed, any other is kept and reported (spec,
  Assumptions). The existing testing-retirement test must stay green.
- Then delete `assets/skills/{backend,frontend,infrastructure}`.
- Existing tests that assume the discipline skills exist must change in this
  task: `writes config, scripts, templates and the engineering skills`
  (expects `.claude/skills/backend/SKILL.md` -- swap for a skill still
  shipped, e.g. `test-first`), the pi step test that expects
  `.pi/skills/backend/SKILL.md` (~line 339), and `the engineering skills name
  the test-first principle instead of the rule`, whose subject no longer exists
  -- delete it. T-0005's `nothing installed points at a discipline skill` may
  drop its folder exclusion.
- Re-running `bun bin/craftpath.ts init` in the worktree retires this
  repository's own installed copies of the three skills -- the real-world check
  of A2. Commit the removals with the task.
- After changing `assets/`, run `bun bin/craftpath.ts init` in the worktree so
  the tracked installed copies under `.claude/`, `.pi/` and `.craftpath/` (and
  `.craftpath/manifest.json`) follow, and commit them with the task -- as
  C-00009 did. Never edit those copies by hand.
