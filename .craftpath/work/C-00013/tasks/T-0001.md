# T-0001 — Refuse review-fix until a point can be fixed

- **Work:** C-00013
- **Type:** feat
- **Wave:** 1
- **Depends on:** none
- **Touches:** assets/scripts/guards/review-fix.py, test/steps/review-fix.test.ts
- **Scenarios:** S9, S10, S11

## Acceptance criteria

- **A1** Given C-00001 whose only task T-0001 is ticked and committed and which has no `REVIEW.md`, when the guard is handed `python3 .craftpath/scripts/review-fix.py C-00001`, then it refuses with a reason containing `no REVIEW.md` and `/craftpath-review C-00001`, and `git status --porcelain` of the worktree is the same before and after — proven by integration test `review-fix is refused without a review, naming the review step`
- **A2** Given C-00001 with T-0001 ticked, T-0002 still open, and a `REVIEW.md` whose Points has `- [ ] R1 [major] src/app.ts:1 -- wrong exit code`, when the guard is handed the review-fix command, then it refuses with a reason naming `T-0002` and containing `not done`, and does not name `T-0001` — proven by integration test `review-fix is refused while a task is open, naming it`
- **A3** Given every task ticked and a `REVIEW.md` whose only points are `R1` marked `[x]` with `(solved in <a real sha>)` and `R2` marked `[-]` with `(won't fix: <reason>)`, when the guard is handed the review-fix command, then it refuses with a reason containing `no review point is open` — proven by integration test `review-fix is refused when every point is closed`
- **A4** Given every task ticked and a `REVIEW.md` whose Points section is `None`, when the guard is handed the review-fix command, then it refuses with a reason containing `no review point is open` — proven by integration test `review-fix is refused when the review has no points`
- **A5** Given every task ticked and committed and a `REVIEW.md` with `R1` open, when the guard is handed the review-fix command, then it lets the call through (no deny decision) — proven by integration test `review-fix runs once every task is done and a point is open`

## Notes

- `guard.py` already maps `.craftpath/scripts/review-fix.py` to
  `guards/review-fix.py` (its pattern allows hyphens), so this task adds only the
  guard file; the script itself is T-0002. The guard can be tested without the
  script: `kit.ts`'s `guard(tree, "review-fix", ID)` builds the command.
- Order of checks: REVIEW.md exists (A1), no open task (A2, reuse the review
  guard's message and `plan_tasks`), at least one `[ ]` point via
  `checks.review_points` (A3, A4). Name the step with `command("review")` /
  `command("work")` so pi users see `/skill:craftpath-…`.
- Decision: the guard does not re-run `check_review` or the "every ticked task has
  a commit" check of the review guard. Reason: S9-S11 name exactly these three
  refusals, and the review step already refused to end with an incomplete
  `REVIEW.md`; a malformed point line is simply not a point.
- Fixtures: `done()` in `test/steps/kit.ts` gives T-0001 ticked and committed;
  write `REVIEW.md` in its Points form (see `assets/templates/REVIEW.md`).
- Implementation: A5's test (the call is let through) passed before the guard
  existed, since a step with no guard file passes straight through. It was seen
  to fail by mutation instead: with the open-point check changed to look for
  `[x]`, A5 failed (and A3 with it); restored, all five pass.
- Implementation: the guard reads `PLAN.md` without checking it exists. A
  `REVIEW.md` can only come from `/craftpath-review`, whose guard requires a
  plan, so a missing plan is not handled separately.
- Implementation: the installed copy under `.craftpath/scripts/guards/` is not
  updated here; re-run `bun bin/craftpath.ts init` once the step lands.
