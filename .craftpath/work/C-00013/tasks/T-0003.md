# T-0003 — Check fix tasks cover every open point

- **Work:** C-00013
- **Type:** feat

## Acceptance criteria

- **A1** Given C-00001 with ticked, committed T-0001, a committed `REVIEW.md` with `R1` and `R2` open, and two new tasks added by task.py with `--type fix`, T-0002 carrying `- **Fixes:** R1` and T-0003 carrying `- **Fixes:** R2`, each with criteria proven by integration tests, when `check.py review-fix C-00001` runs, then it exits 0 and prints `PLAN.md is complete.` — proven by integration test `fix tasks naming every open point pass the review-fix check`
- **A2** Given open points `R1` and `R3` and one new task carrying `- **Fixes:** R1, R3`, when `check.py review-fix C-00001` runs, then it exits 0 — proven by integration test `one fix task may fix several points`
- **A3** Given open points `R1` and `R3` and one new task carrying `- **Fixes:** R1`, when `check.py review-fix C-00001` runs, then it exits 1 and names `R3` as open with no fix task — proven by integration test `an open point no new task fixes fails the review-fix check`
- **A4** Given `R1` open, `R2` marked `[x]` and `R3` marked `[-]`, and a new task carrying `- **Fixes:** R1, R2`, when `check.py review-fix C-00001` runs, then it exits 1 and names `R2` as not open; the same with `R3` in place of `R2` names `R3` — proven by integration test `a fix task naming a closed point fails the review-fix check`
- **A5** Given `R1` open and a new task with no `Fixes` line, when `check.py review-fix C-00001` runs, then it exits 1 and names that task as fixing no point — proven by integration test `a new task without Fixes fails the review-fix check`

## Notes

- Shape, settled here and extended by T-0004 and T-0005: `check_review_fix(work)`
  in `checks.py`, registered as `CHECKS["review-fix"] = ("PLAN.md", check_review_fix)`
  so `check.py review-fix <id>` runs it. It starts from `check_plan(work)`'s
  problems (so it implies `check.py plan` passes) and adds its own.
- A **new task** is a task in `PLAN.md` whose id is not in `PLAN.md` at `HEAD`
  (`git show HEAD:<path>`). Not "an open task": a new task that was wrongly
  ticked must still count as new (T-0005).
- `Fixes` is a header field read with the existing `FIELD` pattern; its value is
  the `R\d+` ids it names. Open points come from `review_points` on the current
  `REVIEW.md`, state `" "`.
- Rules: every new task names at least one point; every named point is open;
  every open point is named by some new task. When there is no new task at all,
  this coverage rule does not apply (S3 -- T-0004 proves that case).
- Decision: a point named by two new tasks is allowed. Alternative: refuse it.
  Reason: no scenario forbids it, and splitting one point's fix across two
  tasks is a planning choice, not an error.
- S2's "no task fixes only R3" depends on the agent judging R3 untestable; no
  check can see that. The step text (T-0006) carries that rule; this check
  proves only the coverage that makes it possible.
- Implementation (T-0003): new tasks are found by comparing `plan_tasks` of
  `git show HEAD:./PLAN.md` (run in the work dir) with the working PLAN.md; a
  PLAN.md missing at HEAD makes every task new. A missing REVIEW.md counts as no
  open point, so each named point is then reported as not open.
- RED was seen in two steps: first all five tests failed with check.py's usage
  exit 2 (no `review-fix` check); with only the registration (`check_plan`), A1
  and A2 passed and A3-A5 failed on exit 0, then went green with the rules.
- Left for later, outside Touches: `check.py`'s docstring still lists only
  `<spec|design|plan>`; its usage line is built from `CHECKS`, so it already
  shows `review-fix`.
