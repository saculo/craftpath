## Acceptance criteria

- **A1** Given a committed plan whose highest wave is 2 (T-0003, ticked), open points R1 and R2 touching the same module, and new fix tasks T-0004 in wave 3 and T-0005 in wave 4, when `check.py review-fix C-00001` runs, then it exits 0 — proven by integration test `fix tasks in waves after the plan pass the review-fix check`

## Notes

- Extends `check_review_fix` from T-0003. "The finished plan's highest wave" is
  the highest wave of HEAD's `PLAN.md`; every new task's wave must be above it.
- Two new tasks touching one module in the same wave are already refused by
  `check_plan`, which `check_review_fix` includes -- S4's "never sharing a
  module within one wave" needs no new rule; A1 shows the passing layout.
- A1 builds on T-0003's passing case; write A2 and A3 first and see them fail.
- Implementation note: A1 passed the first time it ran, as these Notes said it
  would (it builds on T-0003's passing case); A2 and A3 were seen to fail with
  exit 0 before the wave and ticked checks existed. A1's fixture needs a
  two-module config (`app`, `docs`) committed in the test: with one module,
  the finished plan's T-0001/T-0002 (wave 1) or T-0003 would share a module in
  one wave and `check_plan` would refuse the finished plan itself. A2's new
  task touches `docs/guide.md` so the wave rule is its only problem, not the
  existing one-module-per-wave rule.
- With no committed PLAN.md the highest finished wave counts as 0, so every
  wave is "after" it.
