# T-0006 — Install the review-fix step on both harnesses

- **Work:** C-00013
- **Type:** feat
- **Wave:** 6
- **Depends on:** T-0001, T-0002, T-0003
- **Touches:** assets/steps/review-fix.md, README.md, test/steps/review-fix.test.ts
- **Scenarios:** S2, S3, S7, S12

## Acceptance criteria

- **A1** Given a fresh project initialised with `--harness claude-code,pi`, when `craftpath init` installs the steps, then `.claude/skills/craftpath-review-fix/SKILL.md` and `.pi/skills/craftpath-review-fix/SKILL.md` both exist and both contain `python3 .craftpath/scripts/review-fix.py` and `python3 .craftpath/scripts/check.py review-fix` — proven by integration test `review-fix is installed on both harnesses, running the same script and check`
- **A2** Given that project, when its installed review-fix step is read on each harness, then it adds tasks with `task.py <work id> --wave <n> --type fix`, says not to run `complete.py` or the work step, and its report points to `/craftpath-work <work id> all` on Claude Code and `/skill:craftpath-work <work id> all` on pi — proven by integration test `review-fix adds fix tasks and stops, pointing to work`
- **A3** Given that project, when its installed review-fix step is read, then it says an untestable point is put in the `Fixes` of a task for a testable point, never in a task of its own, and that with only untestable points it adds no task and tells the user to fix them by hand or mark them won't fix — proven by integration test `review-fix keeps untestable points out of tasks of their own`
- **A4** Given `assets/steps/review-fix.md` exists, when the README's step names are compared with the steps init installs, then they match, `/craftpath-review-fix` included — proven by integration test `names every step init installs, and no other`

## Notes

- Model the step on `assets/steps/review.md` and `plan.md`: `{{DELEGATE}}`,
  `argument-hint: <work id>`, load `never-block-on-the-human`, `test-first`,
  `sequence-verifiable-units`; step 1 runs `{{SCRIPT:review-fix}} {{ARGS}}` and
  stops on refusal word for word; the agent changes only `PLAN.md` and new task
  files; each task gets `- **Fixes:** R<n>, ...` after `Scenarios`, criteria
  derived from its points, each proven by a named integration or e2e test; it
  ends with `{{SCRIPT:check}} review-fix <work id>`; it reports the new tasks
  and `{{CMD:work}} <work id> all`.
- A fix task still names the `SPEC.md` scenarios whose behaviour it corrects --
  `check_plan` requires Scenarios, and every reviewed change belongs to one.
- A4's test already exists in `test/readme.test.ts` and goes red the moment
  the step file is added: add the step first, see it fail, then add the README
  row (Needs: every task done, an open review point; Writes: fix tasks in
  `PLAN.md`; Then you: `/craftpath-work <id> all`, then review again).
- Decision: `review.md`'s closing report is not changed to mention review-fix.
  Reason: no scenario asks for it; the README row is where the flow is listed.
- The guard is shared by both harnesses through `guard.py` (T-0001), so S12's
  "same guard" needs no harness-specific test.
- Implementation note: A2 and A3 are proven by reading the installed skill on
  both harnesses, word-normalised and split into sentences; the tests look for
  the sentence that names `complete.py` with a "not", and for the sentences
  about "untestable point" and "only untestable points". Rewording those
  sentences in `assets/steps/review-fix.md` means updating the tests with them.
  Both were also seen to fail on a mutated wording, not only on the missing file.
- The installed copies under `.claude/` and `.pi/` of this repo were not
  regenerated (`bun bin/craftpath.ts init`); that is outside this task's Touches.
