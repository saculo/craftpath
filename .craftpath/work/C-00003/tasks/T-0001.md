## Acceptance criteria

- **A1** Given a fresh project with no craftpath installed, when `init --harness claude-code` runs, then `.claude/skills/never-block-on-the-human/SKILL.md` exists, its front matter has the line `name: never-block-on-the-human` and a non-empty `description:`, and the file contains no `{{` — proven by integration test `installs the never-block-on-the-human principle on Claude Code`
- **A2** Given a fresh project, when `init --harness claude-code` runs, then the installed `never-block-on-the-human/SKILL.md` contains neither `disable-model-invocation: true` nor `context: fork`, and neither `.claude/skills/craftpath-never-block-on-the-human` nor `.claude/commands` exists — proven by integration test `the principle is a skill the model loads, not a step the user runs`
- **A3** Given a fresh project, when `init --harness claude-code,pi` runs, then `.pi/skills/never-block-on-the-human/SKILL.md` exists, contains no `{{`, and its `name:` and `description:` front-matter values are identical to those of the Claude Code copy — proven by integration test `installs the same principle on pi`
- **A4** Given the installed principle, when its text is read, then it contains each of the terms `scope`, `intent`, `user-visible behaviour` (the three cases that warrant stopping to ask), `*how*` (the questions the step decides itself) and `reason` (a decision is written down with its reason) — proven by integration test `the principle says when to stop and when to decide`
- **A5** Given the installed principle, when its text is read, then it contains none of `SPEC.md`, `PLAN.md`, `DESIGN.md`, `REVIEW.md`, `Notes` or `Open questions` — it says decisions are written down where the user will see them, never where each step writes them — proven by integration test `the principle does not say where a step writes its decisions`

## Notes

- Skills: `backend` (the discipline closest to this: a shipped asset proven
  through `init`). No `src/` change is expected: `init` already installs every
  `assets/skills/<name>/SKILL.md` on each harness through `harness.render`,
  which adds no step front matter. If A1-A3 pass on the first run once the
  asset exists, that is why -- write A1 first, see it fail on the missing file,
  then add the asset.
- The skill's front matter is `name` and `description` only, like
  `assets/skills/backend/SKILL.md`. The description must make the model load it
  when a step is about to ask the user something, and say it is a rule of
  conduct the spec, plan, work and review steps load -- not an engineering
  discipline.
- Content the skill must carry (S3), in craftpath's own words (work item, spec,
  step, task), not pstack's text:
  - stop and ask only when continuing would change *what* gets built: scope,
    intent, or a user-visible behaviour the spec did not settle;
  - every question about *how* -- naming, which of two equivalent mechanisms,
    the wording of a criterion -- is the step's to decide, not to ask;
  - every decision taken this way is written down, with its reason, where the
    user will see it, so they can correct it afterwards.
  It must not say *where* each step writes its decisions (out of scope; later
  specs). A5's forbidden terms keep it honest -- avoid even mentioning them in
  passing.
- The A4/A5 tests read the installed Claude Code copy; one harness is enough
  for content, since A3 proves pi gets the same file.
- Edit `assets/`, never an installed copy. Refreshing the repo's own `.claude/`
  and `.pi/` copies with `bun bin/craftpath.ts init` is not part of this task.

  work and review steps load, and that the model should load it whenever it
  is about to ask the user something.
