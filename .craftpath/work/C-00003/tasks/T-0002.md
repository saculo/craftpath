# T-0002 — Deciding steps load the principle

- **Work:** C-00003
- **Type:** feat
- **Wave:** 2
- **Depends on:** T-0001
- **Touches:** assets/steps/spec.md, assets/steps/plan.md, assets/steps/review.md, assets/steps/work.md, test/init/init.test.ts
- **Scenarios:** S4, S5, S6, S7, S8

## Acceptance criteria

- **A1** Given a fresh project, when `init --harness claude-code,pi` runs, then each of the installed `craftpath-spec`, `craftpath-plan` and `craftpath-review` skills, on both harnesses, contains ``Load the `never-block-on-the-human` skill``, and that sentence appears before the step's first numbered instruction (the first line starting `1. `) — proven by integration test `spec, plan and review load the principle before their work`
- **A2** Given a fresh project, when `init --harness claude-code,pi` runs, then in the installed `craftpath-work` skill on both harnesses, the text after `## The brief for each task's subagent` contains ``load the `never-block-on-the-human` skill`` (either case of `L`) in the same paragraph as `engineering skills its Notes name` — proven by integration test `work's brief tells each task's subagent to load the principle`
- **A3** Given a fresh project, when `init --harness claude-code,pi` runs, then none of the installed `craftpath-brainstorm`, `craftpath-design`, `craftpath-pr`, `craftpath-learn` and `craftpath-learn-apply` skills, on either harness, contains `never-block-on-the-human` — proven by integration test `steps outside the four do not load the principle`
- **A4** Given the sources in `assets/steps/`, when every skill named in the form ``load the `<name>` skill`` (either case of `L`) is collected, then each name has a file at `assets/skills/<name>/SKILL.md`, and the collected names include `never-block-on-the-human` — proven by integration test `every principle a step loads ships as a skill`
- **A5** Given a project installed with an earlier release -- a copy of `assets/` without `skills/never-block-on-the-human/` and with the load sentence removed from the four steps -- in which the user then edited `.craftpath/templates/SPEC.md`, when `init --harness claude-code` runs with the current assets, then `.claude/skills/never-block-on-the-human/SKILL.md` is written, the four installed `craftpath-spec`, `craftpath-plan`, `craftpath-review` and `craftpath-work` skills contain `never-block-on-the-human`, and the edited `SPEC.md` template is left byte-for-byte as the user wrote it, with the new version in `SPEC.md.new` — proven by integration test `re-running init adds the principle without overwriting your edits`

## Notes

- Skills: `backend`.
- Wording, decided here (local to this task): a step names a principle with
  the sentence ``Load the `<name>` skill`` -- that phrase is what A4's test
  collects, so later principles follow the same pattern with no change to
  `init` or `harness.ts`. The engineering skills are named differently
  (design's "the `architecture` skill", work's "engineering skills its Notes
  name"), so they are not collected; if they were, they would still pass A4,
  since they ship under `assets/skills/` too.
- spec, plan, review: put the sentence directly under the step's `#` heading,
  before anything else in the body -- in spec that is above the "If the request
  starts with an existing work item's id" paragraph, so revising a spec loads
  it too. On pi the hand-off paragraph sends "everything below this
  paragraph" to the subagent, so the sentence must be below `{{DELEGATE}}`,
  which the heading already is. Suggested text: ``Load the
  `never-block-on-the-human` skill before you do anything else.``
- work: the sentence goes in the brief, next to "Load the engineering skills
  its Notes name" -- not in the orchestrating part of the step, which decides
  nothing. Do not add it to the session's own instructions.
- Do not touch the steps' existing instructions about questions ("Do not
  invent answers", the brief's `STUCK`): out of scope; later specs revise them.
- Do not touch brainstorm, design, pr, learn or learn-apply (A3).
- A5 builds its "earlier release" fixture the way the existing test `a file
  you did not edit takes the new version; one you edited is kept, the new one
  beside it` does: `cp` `assets/` to a scratch dir, then delete
  `skills/never-block-on-the-human/` and strip the load sentence from the four
  step copies. Install that first, edit the SPEC.md template, then re-run
  `init` with the real assets.
- A3 and A5's "kept" half guard behaviour that already holds and may pass on
  the first run; if so, show each can fail (e.g. temporarily add the sentence
  to `pr.md`; temporarily overwrite on re-run) and restore, and record that
  under Notes, as C-00001's T-0002 did.
- Edit `assets/`, never an installed copy. Refreshing the repo's own `.claude/`
  and `.pi/` copies with `bun bin/craftpath.ts init` is not part of this task.

### Implementation notes (T-0002)

- spec, plan, review: ``Load the `never-block-on-the-human` skill before you
  do anything else.`` directly under the `#` heading (below `{{DELEGATE}}`, so
  pi's hand-off carries it; in spec, above the revise-a-spec paragraph).
- work: the brief now reads "Load the engineering skills its Notes name, and
  load the `never-block-on-the-human` skill." -- same sentence, so A2's
  same-paragraph check holds; the paragraph was rewrapped.
- The tests compare words, not lines: a helper strips the brief's `> `
  blockquote prefix and collapses whitespace, so a sentence that wraps still
  matches. A2 splits the brief into paragraphs on blank / bare `>` lines.
- A4 collects ``[Ll]oad the `<name>` skill`` from `assets/steps/*.md` (word-
  collapsed), and today finds only `never-block-on-the-human`.
- A5: the "earlier release" fixture strips the load sentence with a regex and
  asserts the stripped copies no longer mention the principle. `SPEC.md.new`
  is compared with the template a fresh install writes, not the raw asset --
  templates are rendered at install (`{{CMD:plan}}` becomes `/craftpath-plan`),
  which my first version of the test got wrong.
- Seen failing: A1, A2, A4 and A5 failed before the step edits, on the
  missing sentence. A3 passed on its first run (behaviour already held);
  shown it can fail by temporarily adding the sentence to `assets/steps/pr.md`
  (failed), then restored. A5's "kept" half shown it can fail by temporarily
  making `src/install.ts` overwrite an edited file instead of writing `.new`
  (failed), then restored.
- Out of scope, not done: the repo's own installed `.claude/` and `.pi/`
  copies were not refreshed.
