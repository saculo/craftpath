## Acceptance criteria

- **A1** Given a project initialized with both Claude Code and pi, when `craftpath init --harness claude-code,pi` installs the assets, then both harnesses contain `test-behaviour-not-implementation/SKILL.md` with guidance to use real owned boundaries, mock only unowned systems, make and name one observable behaviour claim per test, and keep tests independent of order; neither rendered skill contains unresolved asset tokens — proven by integration test `installs the behaviour-testing principle on both harnesses`.
- **A2** Given a project initialized for Claude Code and pi, when each harness renders the spec workflow instructions, then each installed spec skill instructs its agent to load `test-behaviour-not-implementation` before writing scenarios, and does not substitute implementation-detail testing guidance — proven by integration test `spec instructions load the behaviour-testing principle`.
- **A3** Given a project initialized for Claude Code and pi, when each harness renders the work workflow instructions, then each installed work skill tells every implementation subagent to load `test-behaviour-not-implementation` before its test-first cycle, and does not omit the existing TDD instruction — proven by integration test `work instructions load the behaviour-testing principle before TDD`.
- **A4** Given a project initialized for Claude Code and pi, when each harness renders the review workflow instructions, then each installed review skill instructs its reviewer to load `test-behaviour-not-implementation` while assessing task-proving tests, and does not remove the requirement to review every acceptance criterion — proven by integration test `review instructions load the behaviour-testing principle`.
- **A5** Given a project initialized from an earlier asset set that contains the managed `testing` skill, when it is reinitialized from the updated assets for Claude Code and pi, then neither harness retains the managed `testing` skill and the updated plan instructions do not name `testing` for implementers — proven by integration test `reinitializing retires the managed testing skill`.

## Notes

Follow the repository TDD rule: add each named integration test first, run `bun test test/init/init.test.ts` and observe its intended failure before changing production assets or initializer code. The initializer currently writes assets but never removes stale skill directories; make retirement compatible with its manifest-based ownership model so a managed obsolete skill is removed without deleting an edited user file. Update cross-skill references that describe the retired skill so the installed guidance has one testing principle. No additional engineering skill is needed.

Implementation decisions:
- Retirement runs only when the source asset set no longer contains `testing`, so an older asset set can still install the skill during the update test.
- The initializer compares the installed file to its manifest hash and deletes only an unchanged managed skill; edited files are retained and reported.
- The retired skill directory may remain empty after its managed file is removed; harnesses load `SKILL.md`, so removal is observable without risking an edited directory's contents.
- User decision after review: retain the backend and frontend skills unchanged; their existing references to `testing` are out of scope here and will be addressed by the later discipline-skills work item.
