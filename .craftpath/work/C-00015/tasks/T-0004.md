# T-0004 — Install the verify step: find, then refute

- **Work:** C-00015
- **Type:** feat
- **Wave:** 4
- **Depends on:** T-0003

## Acceptance criteria

- **A1** Given a project after `craftpath init --harness claude-code,pi`, when its installed `craftpath-verify` step is read on each harness, then it tells the step to start one finder agent that reads `SPEC.md`, `PLAN.md`, the task files and `git diff` of the range the script printed, and proposes findings each stating an input or state, what goes wrong, and a `file:line`; and the step's text does not contain `DECISIONS.md` — proven by integration test `S7 the finder reads the spec, plan, tasks and diff, never DECISIONS.md`
- **A2** Given the same project, when its installed `craftpath-verify` step is read on each harness, then it tells the step to start a second agent in a fresh context, given only the proposed findings and the worktree, that tries to refute each finding by reading the code and, where it can, by running it or writing a throwaway test it deletes afterwards — proven by integration test `S7 the refuter gets only the findings and the worktree, and may run the code`
- **A3** Given the same project, when its installed `craftpath-verify` step is read on each harness, then it says only findings the refuter could not refute are added to `VERIFY.md` as new `F<n>` points, that a refuted finding and one without a failure scenario are written into no file, and that style, naming and formatting are never findings — proven by integration test `S8 only findings the refuter could not refute become points`
- **A4** Given a `config.toml` with `[steps.work.claude-code] model = "sonnet"`, `[steps.verify.claude-code] model = "opus"`, `effort = "high"` and the same split under `[steps.work.pi]` (`model = "openai-codex/gpt-5.6-terra"`) and `[steps.verify.pi]` (`model = "anthropic/claude-opus-5-5"`, `effort = "high"`), when `craftpath init --harness claude-code,pi` runs, then the Claude Code verify step names ``model `opus`, effort `high` `` for both the finder and the refuter (twice) and never `sonnet`, its front matter has no `model:`, `effort:` or `context: fork` line, and the pi verify step names ``model `anthropic/claude-opus-5-5`, thinking level `high` `` twice and never work's model — proven by integration test `S9 finder and refuter both start with verify's model and effort, never work's`
- **A5** Given a `config.toml` that sets `[steps.work.claude-code]` and `[steps.work.pi]` and no `[steps.verify.*]`, when `craftpath init --harness claude-code,pi` runs, then neither installed verify step contains ``model ` ``, ``effort ` `` or ``thinking level ` ``, and the Claude Code one has no `model:` or `effort:` front-matter line — proven by integration test `S10 without verify settings, finder and refuter run on the session model`

## Notes

- `assets/steps/verify.md` replaces what `review.md` did, in the review step's
  numbered shape: run `{{SCRIPT:verify}} {{ARGS}}` (stop and report a refusal
  word for word); start the finder; start the refuter with the finder's
  findings; re-check every open point against the code, marking `[x]` with
  `(solved in <sha>)` only when a commit in the range solved it; add each
  confirmed finding as the next point from the id the script printed, in
  T-0001's shape (`- [ ] F<n> [major|minor] <file:line> -- given <input or
  state>, <what goes wrong>`); never delete, renumber, reword or mark won't
  fix; `None` when there is no point; run `{{SCRIPT:check}} verify <work id>`;
  stop and report. Next steps: `{{CMD:learn}}` (optional), then `{{CMD:pr}}`.
  Do not delete `review.md`: T-0007 retires it.
- **Verify runs in the session, like work.** Decided: no `{{DELEGATE}}` in
  `verify.md`. `src/harness.ts` says a forked step's subagents do not wait for
  it, and verify starts two that run one after the other. So on Claude Code
  verify's settings go to the two `Agent` calls (`{{SUBAGENT}}`, as work does),
  not to its front matter. Rejected: forking verify with `model:` front matter
  as review had -- the finder's result would never reach the refuter.
- In `src/harness.ts`, generalize the `step === "work"` special case to "a step
  whose source carries `{{SUBAGENT}}`" (work and verify), on both harnesses,
  rather than adding `|| step === "verify"`: the token already says the step
  starts its own subagents. Work's rendering must not change -- the existing
  work-settings tests in `test/init/init.test.ts` stay green unchanged.
- Each `Agent` call is written as work's is -- agent `general-purpose`
  followed by `{{SUBAGENT}}` -- so with
  settings unset nothing is named (S10) and work's setting never leaks in: it
  is read from `configured["verify"]` only.
- Decided: the finder's brief loads `test-first`,
  `test-behaviour-not-implementation`, `fix-root-causes` and
  `laziness-protocol` -- review's principles, because a fresh subagent loads
  nothing the step loaded -- and the step itself loads
  `never-block-on-the-human`. Carry review's *How to review* checks (spec and
  plan coverage, hollow tests, nothing outside the plan, out of scope,
  correctness, security, boundaries, root causes, smallest change) into the
  finder's brief, minus the "every recorded decision holds" check (S7: no
  `DECISIONS.md`) and minus "clarity" items that are naming or style (S8).
- The refuter's brief: the findings verbatim and the worktree path, nothing
  else (no spec, no plan); it answers per finding `confirmed` or `refuted`
  with the evidence, and deletes any test it wrote before it ends.
- `README.md`: add a `/craftpath-verify <id>` row to the steps table (what it
  needs, what it writes, what you do next) -- `test/readme.test.ts` fails
  otherwise once `assets/steps/verify.md` exists. Leave the review row: T-0007
  removes it.
- Re-run `bun bin/craftpath.ts init` in the worktree and commit the installed
  copies (both harnesses) with the task.
