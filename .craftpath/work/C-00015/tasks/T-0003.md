# T-0003 — Run tests first, then bind VERIFY.md to HEAD

- **Work:** C-00015
- **Type:** feat
- **Wave:** 3
- **Depends on:** T-0001
- **Touches:** assets/scripts/verify.py, assets/scripts/checks.py, assets/templates/VERIFY.md, test/steps/verify.test.ts, test/steps/kit.ts, .craftpath/scripts/verify.py, .craftpath/scripts/checks.py, .craftpath/templates/VERIFY.md
- **Scenarios:** S3, S4, S5

## Acceptance criteria

- **A1** Given C-00001 with every task done and committed and a later commit that makes the module's `test` command fail, when `verify.py C-00001` runs, then it exits 1 with the test's output, no `VERIFY.md` exists and HEAD has not moved — proven by integration test `S3 with a module's tests red, exits 1 with their output and creates no VERIFY.md`
- **A2** Given the same work item with its tests green and a module `check` command that prints `check failed` and exits 1, when `verify.py C-00001` runs, then it exits 1 with `check failed` in its output, no `VERIFY.md` exists and HEAD has not moved — proven by integration test `S3 with a module check red, exits 1 and neither writes nor commits`
- **A3** Given C-00001 with tests and checks green and no `VERIFY.md`, when `verify.py C-00001` runs, then it creates `.craftpath/work/C-00001/VERIFY.md` holding `- **Verified at:** ` followed by HEAD's full sha, prints the base..HEAD range, the commit `feat(C-00001/T-0001): Add GET /health`, the file `src/app.ts`, `Open points: none` and `next point: F1`, and no `REVIEW.md` exists — proven by integration test `S4 without VERIFY.md, creates it verified at HEAD and says what to verify`
- **A4** Given a `VERIFY.md` verified at an older commit holding `F1` open and `F2` solved, and a newer commit on the branch, when `verify.py C-00001` runs, then both point lines are unchanged and in their order, `Verified at` names the new HEAD, the output lists `F1` under the open points and not `F2`, and prints `next point: F3` — proven by integration test `S5 a re-run keeps every point, moves Verified at to HEAD and gives F3`
- **A5** Given C-00001 with green tests and an uncommitted `DECISIONS.md` in its work directory, when `verify.py C-00001` runs, then the newest commit before verifying is `docs(C-00001): add decisions` and it changes `DECISIONS.md` alone, and the output does not print `DECISIONS.md`'s path among what to verify — proven by integration test `commits an uncommitted DECISIONS.md alone before verifying`
- **A6** Given a `VERIFY.md` with `None` under Points that passes `check.py verify`, when `verify.py C-00001` runs again, then HEAD is a new commit with subject `docs(C-00001): add verify`; and with an open point instead, no commit is made — proven by integration test `commits a VERIFY.md with no open point as the verify record`

## Notes

- `verify.py` is `review.py` renamed into the new vocabulary: `Verified at`,
  `VERIFY.md`, `F<n>`, `verify_points`, and `command("verify")` for the
  usage message. Keep `review.py` untouched: T-0007 removes it.
- Unlike `review.py`, `verify.py` does not print `DECISIONS.md`'s path among
  what to read: S7 keeps it from the agents. It still commits it (SPEC.md
  assumption) and may print that commit's `<short sha> <subject>`.
- Add to `checks.py`: `verify_points(text)` (state, id, line for every
  well-formed `F` point, used for the open list and the next id) and
  `verify_closed(work, work_id)`, returning the text and refusing while
  `VERIFY.md` is missing, incomplete, or has an open point. Word the refusals
  as `review_closed` does, with verify in place of review:
  - missing: `There is no VERIFY.md yet -- run /craftpath-verify C-00001 first.`
  - open: `These verify points are open -- fix each and run /craftpath-verify C-00001 again, or mark it won't fix:`
    followed by the open lines.

  T-0005 and T-0006 build the learn and pr guards on it. Use `command('verify')` so each harness is named.
- Kept as one task with six criteria rather than split: the tests-first gate
  (A1, A2) and the file it guards (A3, A4) are accept-and-reject of one
  script, and the two commits (A5, A6) are what review already did on every
  run -- dropping them would make verify lose DECISIONS.md for learn and pr.
- `assets/templates/VERIFY.md`, after `REVIEW.md`: title
  `# {{ID}} — {{TITLE}}: verify`, `- **Verified at:** {{SHA}}`, a `## Points`
  section and a guidance comment giving the point shape from T-0001, the
  `[x] ... (solved in <sha>)` and `[-] ... (won't fix: <reason>)` forms, and
  that `{{CMD:pr}}` refuses while a point is open.
- A6 is review's "commits a completed review automatically" carried over: the
  assumption "points keep review's lifecycle" in SPEC.md.
- The docstring at the top of `verify.py` says what it does; write it, the
  guard reads nothing from it.
- Add `verify(tree)` to `test/steps/kit.ts`, the work item's `VERIFY.md`
  path, beside `review(tree)`; T-0005 and T-0006 use it, T-0007 removes
  `review`.
- Re-run `bun bin/craftpath.ts init` in the worktree and commit the installed
  copies with the task.
