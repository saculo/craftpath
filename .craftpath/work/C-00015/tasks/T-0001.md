## Acceptance criteria

- **A1** Given C-00001 with every task done and a `VERIFY.md` whose `Verified at` is HEAD and whose only point is `- [ ] F1 [major] src/a.ts:12 -- given an empty list, total() returns NaN instead of 0`, when `check.py verify C-00001` runs, then it exits 0 and prints `VERIFY.md is complete.` — proven by integration test `S6 a point with a location and a failure scenario passes`
- **A2** Given the same `VERIFY.md` with `None` under Points, when `check.py verify C-00001` runs, then it exits 0 — proven by integration test `S6 None under Points passes`
- **A3** Given a `VERIFY.md` with the open point `- [ ] F1 [major] src/a.ts:12 -- total() is wrong`, when `check.py verify C-00001` runs, then it exits 1 and its output names `F1` as missing its failure scenario, and does not name `F1` as missing its location — proven by integration test `S6 names a point without a failure scenario by id`
- **A4** Given a `VERIFY.md` with the open point `- [ ] F2 [minor] src/a.ts -- given an empty list, total() returns NaN`, when `check.py verify C-00001` runs, then it exits 1 and its output names `F2` as missing its `file:line` location — proven by integration test `S6 names a point without a file:line by id`
- **A5** Given a `VERIFY.md` holding an `R1` point, `F3` twice, an `[x]` point without `(solved in <sha>)` and a `[-]` point without `(won't fix: <reason>)`, when `check.py verify C-00001` runs, then it exits 1 and names each of the four problems — proven by integration test `names a review-style id, a duplicate, an unsolved [x] and a reasonless [-]`

## Notes

- Add `check_verify` beside `check_review` in `assets/scripts/checks.py` and
  register `"verify": ("VERIFY.md", check_verify)` in `CHECKS`. Leave
  everything review-related in place: T-0007 removes it.
- The point shape: `- [ |x|-] F<n> [major|minor] <file:line> -- given <input
  or state>, <what goes wrong>`. Decided: the location is `\S+:\d+` (a path,
  a colon, a line number), the failure scenario is the text after ` -- `
  starting with `given ` (either case) and holding a `, ` followed by the
  outcome. Rejected: a free-form "anything after `--`" as review had -- S6
  needs a mechanical difference between a scenario and a complaint.
- Decided: the scenario and location rules apply to every point, whatever
  its state, not only open ones. Points are never reworded, so a point that
  passed when it was written still passes once it is solved or won't fix;
  checking only open points would let a malformed point through the moment
  the user marks it `[-]`.
- `Verified at` must name a commit, the same rule review had for `Reviewed at`.
  A test writes it with the work item worktree's HEAD sha (`done()` in
  `test/steps/kit.ts` gives a work item with T-0001 completed).
- Write a malformed point that has no location *and* no scenario as one
  problem per missing part, each naming the id, so the user can fix both in one
  pass.
- Re-run `bun bin/craftpath.ts init` in the worktree after changing `assets/`
  and commit the installed copy with the task (CLAUDE.md: change `assets/`,
  never the copies).
