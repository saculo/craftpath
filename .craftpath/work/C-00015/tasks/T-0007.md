## Acceptance criteria

- **A1** Given a project with Claude Code and pi installed by an earlier release that shipped the review step, when `craftpath init` runs again, then `.claude/skills/craftpath-verify/SKILL.md` and `.pi/skills/craftpath-verify/SKILL.md` exist, `.claude/skills/craftpath-review/SKILL.md` and `.pi/skills/craftpath-review/SKILL.md` do not, and the output reports `removed   ` for each of the two — proven by integration test `S1 re-running init replaces the review step with verify on both harnesses`
- **A2** Given the same earlier install, unedited, when `craftpath init` runs again, then `.craftpath/scripts/review.py`, `.craftpath/scripts/guards/review.py` and `.craftpath/templates/REVIEW.md` no longer exist and none is listed in `.craftpath/manifest.json` — proven by integration test `S1 re-running init removes review's script, guard and template`
- **A3** Given the same earlier install with `.claude/skills/craftpath-review/SKILL.md` edited by the user, when `craftpath init` runs again, then that file is still there unchanged and the output reports `kept      .claude/skills/craftpath-review/SKILL.md (edited)` — proven by integration test `S1 re-running init keeps an edited review step`
- **A4** Given a project after `craftpath init --harness claude-code,pi`, when every file under `.claude/`, `.pi/`, `.craftpath/scripts/` and `.craftpath/templates/` is read, then none contains `/craftpath-review` or `/skill:craftpath-review` — proven by integration test `S1 no installed step, script or template names the review step`
- **A5** Given this repository's `README.md` and `CLAUDE.md`, when they are read, then each names `/craftpath-verify` and neither names `/craftpath-review`, and the README shows `[steps.verify.claude-code]`, not `[steps.review.claude-code]` — proven by integration test `S1 README and CLAUDE.md name verify, never review`
- **A6** Given a project with no `config.toml`, when `craftpath init` runs, then the written `config.toml` shows the commented `# [steps.verify.claude-code]` and `# [steps.verify.pi]` examples and no `steps.review` — proven by integration test `S1 the fresh config.toml shows verify's settings`

## Notes

- Kept as one task with six criteria: deleting `assets/steps/review.md`
  forces the README and the init tests to change in the same commit
  (`test/readme.test.ts` requires the README to name exactly the shipped
  steps), and a split would leave one commit where the step is gone but
  something still tells the user to run it -- the very thing S1 forbids.
- Delete `assets/steps/review.md`, `assets/scripts/review.py`,
  `assets/scripts/guards/review.py`, `assets/templates/REVIEW.md`, and from
  `checks.py` `review_points`, `check_review`, `review_closed` and the
  `"review"` entry in `CHECKS`. Rename `POINT` if only `F` points remain.
- Retirement in `src/init.ts`: extend the existing `retireSkills` mechanism
  (manifest hash decides unedited, a user's edit is kept and reported, a file
  never in the manifest is the user's and left alone) to the review step on
  each *selected* harness and to the three shared files, keyed on the asset
  set no longer shipping `steps/review.md`, `scripts/review.py`,
  `scripts/guards/review.py`, `templates/REVIEW.md`. Rejected: removing every
  manifest file not written this run -- a run with `--harness claude-code` on
  a project that also has pi would delete pi's whole install.
- The earlier-release fixture: copy `assets/` to a scratch dir and add the
  four review files back (as `test/init/init.test.ts` already does for the
  retired testing skill), init with it, then init with the real assets.
- Text that still points at review: `assets/steps/work.md` (the next step is
  `{{CMD:verify}}`; DECISIONS.md is committed by the verify step),
  `assets/templates/KNOWLEDGE.md` (`review R3` becomes `verify F3`), the
  descriptions of `never-block-on-the-human` and `test-first` ("the spec,
  plan, work and verify steps"), the `src/cli.ts` header comment, and
  `writeConfig` in `src/init.ts` (`[steps.verify.*]` examples; its comment
  says verify's setting, like work's, applies to the subagents it starts, so
  its model must be an alias on Claude Code). README: remove the review row,
  `REVIEW.md` in the file tree, the `[steps.review.claude-code]` example; say
  verify where it says review. `CLAUDE.md`: the flow line lists
  `/craftpath-verify` (SPEC.md assumption).
- Tests: delete `test/steps/review.test.ts` -- its guard and script cases are
  covered by `test/steps/verify.test.ts` (T-0001 to T-0003), and its "review
  checks recorded decisions" cases are deliberately dropped: S7 forbids
  giving `DECISIONS.md` to the agents. Move "only review, learn and pr name
  DECISIONS.md among the scripts" to verify, learn and pr. In
  `test/init/init.test.ts` replace `review` by `verify` in `STEPS` and in the
  principle-loading tests; the per-step settings tests that used review as
  the forked example (`[steps.review.claude-code]` -> front matter) move to
  `plan`, since verify runs in the session. Remove `review(tree)` from the
  kit.
- Evals (`evals/llm/`): E2, E3 and E6 run `verify` instead of `review`; the
  fixtures write `VERIFY.md` through `verify.py`, with `F1` in the failure
  scenario shape (`- [ ] F1 [major] src/clamp.ts:1 -- given min 10 and max
  0, clamp(5, 10, 0) returns 5 instead of throwing a RangeError`); the graders
  read `VERIFY.md`, `F` points and `check.py verify`. `graders.test.ts` must
  stay green. No new eval: measuring verify is out of scope.
- Re-run `bun bin/craftpath.ts init` in the worktree: it removes this repo's
  installed review step on both harnesses and the review scripts, and installs
  the updated copies. Commit them with the task.
